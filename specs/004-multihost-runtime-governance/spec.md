# Feature Specification: 跨宿主 SDD 运行时治理层（v2.0）

> Describe **what** the system must do and **what it must NOT do**. Keep implementation details (SQL, frameworks, internal classes) out of this document.

## 1. User Story & Intent

- **作为一名**已经用本套件在 DSH 里跑通 Spec Kit 闭环、并希望把同一套 SDD 纪律带到 Claude Code / Codex / Cursor 的开发者，**我希望**治理价值本身与终端解绑——纪律提示在会话一开始就常驻且抗压缩、出问题一次只读体检就能定位、改动后明确知道要不要重启或新开会话、换终端只需换一层薄适配，**从而**让「装了但不生效」变成可解释、可定位、可收敛的少数几种情况，而不是每换一个终端就复制一套逻辑、重攒一遍经验。

**背景与动机**：v0.5.x 已完成供给面瘦身（删除自研安装器与平行写路径，保留两个命名技能、两个宿主工具、一个内置 Spec Kit 扩展），安装与升级不再是风险来源。真正的空白在两处：运行面（技能挂载不等于触发，规划期与上下文压缩后缺乏引导，出问题时缺乏只读诊断面，重载口径散落多处）与扩展面（全部能力长在单一宿主的注册 API 上，接入第二个终端就得复制一套代码）。上游事实支持正确路径：Spec Kit 的集成目录已覆盖数十个宿主且四端均声明可增量共存，Superpowers 亦已覆盖十余个宿主的官方安装通道；因此正确做法不是自建跨端技能桥接器，而是把本套件的治理价值层彻底宿主无关化，顺着上游原生通道抵达每一端。

**用户场景**

- 引导场景（新会话）：用户在一个已有 Spec Kit 产物的仓库里开新会话，首条请求就带上上游纪律正文、当前 feature 与所处阶段的指针；聊到中途发生上下文压缩后，这段引导仍在，不需要用户重新提醒。
- 引导降级场景：用户换了机器或清理了上游镜像目录，插件照常加载、其余功能照常工作，引导静默缺席并留下可读告警，体检如实报告缺什么、怎么修。
- 体检场景（首次接手）：用户在一个陌生项目执行一次只读体检，缺失依赖被一次性列全并附修复命令，报告分为环境、宿主、仓库、运行时、触发试跑五区；重复执行结果一致且不产生任何写入。
- 冲突诊断场景：机器上同时装了多个提供同类技能的插件，体检准确指出同名技能的来源与优先级冲突，而不是让用户面对「技能有时在有时不在」。
- 护栏场景（规划期）：实现已经开始后，用户想顺手改一句 spec，规划期命令被只读护栏拦下并提示先回到定义阶段，而不是让规范在实现中途悄悄漂移。
- 重载场景：用户升级了扩展或改了技能数据，系统明确告知「需要重启宿主」「需要新开会话」或「无需动作」，并留下带时间戳与原因的待生效标记；宿主重启后标记自动消失，体检不会把历史残留误报成本次改动。
- 首个外部端场景：Claude Code 用户按上游官方渠道装好 Superpowers 与本套件后，不改既有习惯就获得 EARS 模板、执行护栏与体检；未装上游插件时得到一句可执行的提示，而不是整段功能失效。
- 多端收官场景：Codex 与 Cursor 用户各自用原生调用方式（`$speckit-*` / `/speckit-*`）跑通同一套动作，Cursor 端的自动信任派发配置被体检显式标为安全风险，四端体检首诊全部可用。
- 漂移发现场景：上游发布破坏性变更，每日/PR 回归矩阵在合并前变红，并指出漂移点与需要调整的版本下界，而不是等用户在项目里踩到。

## 2. Functional Requirements (EARS Format)

每条需求使用 EARS 语法，与其自动化测试一一对应。

**A. 宿主无关核心与适配器契约（FR-001，P0）**

- `REQ-01`: **THE SYSTEM SHALL** 把全部治理能力（镜像同步、更新编排、安装状态机、重载判定、体检探测、引导拼装、模板渲染）收拢在一处宿主无关的核心中；该核心 MUST NOT 引用任何宿主专属的包名、注册 API 或全局对象。
- `REQ-02`: **WHEN** 核心目录中出现任何宿主专属引用 **THE SYSTEM SHALL** 让自动化测试失败并阻断合并，且该断言 MUST 是静态扫描而非运行期抽查。
- `REQ-03`: **THE SYSTEM SHALL** 把每个宿主的能力限定为固定三面（工具面：动作如何被宿主调用；引导面：常驻纪律如何抗压缩注入；技能面：上游技能如何进入目录）加重载语义；适配层 MUST NOT 承载业务逻辑。
- `REQ-04`: **THE SYSTEM SHALL** 为三面契约保留唯一文档化定义（每面的输入、使用的宿主机制、不可用时的降级行为），且新增宿主 MUST 只需实现该契约。
- `REQ-05`: **WHEN** 运行在非 DSH 宿主 **THE SYSTEM SHALL** 通过一个零第三方依赖的命令行入口提供与宿主工具等价的能力（更新、桥接、体检），输出结构与宿主工具 100% 同构。
- `REQ-06`: **WHEN** 新增第二个宿主适配器 **THE SYSTEM SHALL NOT** 需要修改核心逻辑；改动 MUST 限于新增适配实现与宿主能力表条目。
- `REQ-07`: **THE SYSTEM SHALL** 使单个宿主适配实现规模不超过 100 行；超出即视为接缝设计失败。

**B. 会话引导（FR-001 引导面，M2）**

- `REQ-08`: **WHEN** 新会话的首条请求被处理，且上游纪律技能正文可读 **THE SYSTEM SHALL** 注入一段常驻引导，内容 MUST 由三部分组成：上游原文（引用而非复制）、当前宿主的工具名映射、当前 SDD 上下文指针（当前 feature、所处阶段、建议的下一条命令）。
- `REQ-09`: **WHEN** 拼装结果超过 1.2k token 硬上限 **THE SYSTEM SHALL** 只裁剪 SDD 指针部分，MUST NOT 裁剪上游原文；**IF** 上游原文本身即超限 **THE SYSTEM SHALL** 保留原文完整、记录超限告警，并 MUST NOT 因超限而整体放弃注入。
- `REQ-10`: **WHEN** 会话发生上下文压缩 **THE SYSTEM SHALL** 使引导段在压缩后依然存在，且 MUST NOT 需要用户重新触发。
- `REQ-11`: **IF** 上游镜像缺失，或纪律技能被上游改名/移走 **THE SYSTEM SHALL** 静默不注册该引导段、留下一条提示运行安装命令的告警，且 MUST NOT 阻断插件加载与其他任何功能。
- `REQ-12`: **WHEN** 用户关闭引导开关（缺省为开启）**THE SYSTEM SHALL** 不注入任何常驻内容，且技能目录、技能可用性与手动调用 MUST NOT 受影响；开关 MUST 支持两级作用域（仓库内项目级与用户全局级），项目级存在时覆盖全局级，且体检 MUST 报告当前实际生效的那一级。两级开关 MUST 落在既有配置文件的增量键上（用户全局级 `~/.dsh/sdd-kit.json` 与项目级 `<repo>/.specify/sdd-kit.json` 的 `guidance.enabled`），MUST NOT 为此新建独立的开关文件或状态文件；任一配置文件不可解析时 MUST 视为该级未设置并记告警，MUST NOT 使引导整体失败。
- `REQ-13`: **WHEN** 同一份引导被投递到不同宿主 **THE SYSTEM SHALL** 使用同一份拼装结果，各宿主 MUST NOT 各自维护一份引导文案副本。

**C. 更新编排核心化与三态重载（FR-002，P0）**

- `REQ-14`: **WHEN** 宿主工具与命令行入口执行同一动作 **THE SYSTEM SHALL** 走同一核心实现，并以共享样例断言两者输出结构 100% 一致。
- `REQ-15`: **WHEN** 一次改动被提交给重载判定 **THE SYSTEM SHALL** 依据改动层（工具代码 / 技能数据 / 扩展命令）与宿主语义给出唯一结论，结论 MUST 是三种之一：需要重启宿主、需要新开会话、无需动作。
- `REQ-16`: **THE SYSTEM SHALL** 让同一改动集在不同宿主得到各自语义的结论，且该判定 MUST 只有一处实现。
- `REQ-17`: **WHEN** 结论要求用户执行生效动作 **THE SYSTEM SHALL** 落盘一个待生效标记，标记 MUST 含改动层、时间戳、原因与所属宿主，且 MUST 按仓库共享、按宿主分条记录，使同一仓库在不同宿主上的待生效状态互不覆盖且彼此可见。
- `REQ-18`: **WHEN** 宿主在标记存在的情况下完成启动 **THE SYSTEM SHALL** 自动清除该标记，且 MUST NOT 要求用户手工清理；清除 MUST 只作用于当前仓库与当前宿主对应的条目，MUST NOT 影响其他仓库或其他宿主的条目。
- `REQ-19`: **IF** 体检读到残留标记 **THE SYSTEM SHALL** 按时间戳区分「历史未清理」与「本次改动」，前者 MUST NOT 被报告为本次待生效。
- `REQ-20`: **IF** 改动集为空 **THE SYSTEM SHALL** 给出「无需动作」且 MUST NOT 落盘标记。
- `REQ-21`: **WHEN** 在具备宿主运行时的机器上实测依赖版本下界 **THE SYSTEM SHALL** 把宿主专属依赖声明为「实测下界 + 可选」，使纯 Node 环境安装不产生 peer 警告或强制安装要求，且 MUST NOT 改变宿主环境下的既有行为。

**D. 扩展多端复用与规划期护栏（FR-003，P0 / 护栏 P1）**

- `REQ-22`: **WHEN** 内置扩展被装入四个目标集成中的任意一个，且该集成为当前激活集成 **THE SYSTEM SHALL** 使四个执行钩子等价生效（实现前/后、缺陷修复前/后），且 MUST 依托上游的增量共存能力，MUST NOT 自建冲突消解机制；**WHEN** 某集成已安装但非激活集成 **THE SYSTEM SHALL** 如实报告该端钩子命令未被渲染，MUST NOT 声称其已生效，也 MUST NOT 为绕过上游的激活语义而自行写入第二套钩子配置。
- `REQ-23`: **IF** 实现阶段已经开始，而用户触发规划期命令（澄清、计划）**THE SYSTEM SHALL** 以只读方式拦截并提示先回到定义阶段，MUST NOT 修改任何文件，MUST NOT 引入独立的交接状态机；「实现阶段已开始」MUST 由仓库内既有产物推断（当前 feature 的 tasks.md 存在且至少一项任务已勾选），MUST NOT 依赖额外的阶段标记文件。
- `REQ-24`: **THE SYSTEM SHALL** 在扩展清单中声明所需的上游最低版本；**IF** 实际版本低于该下界 **THE SYSTEM SHALL** 在安装期即硬失败并报出所需版本，MUST NOT 留下半装状态，MUST NOT 以「已装好但钩子不生效」的形式继续；预发布版本号（含开发后缀）MUST 得到确定的判定结论，MUST NOT 因版本串不可解析而静默放行。
- `REQ-25`: **WHEN** 同一仓库存在多个集成共存 **THE SYSTEM SHALL** 使各端技能产物互不覆盖，且体检能同时识别全部已装集成。

**E. Claude Code 适配器（FR-004，P0）**

- `REQ-26`: **THE SYSTEM SHALL** 为 Claude Code 提供三面实现：技能面声明并检测官方插件渠道的纪律技能安装；工具面默认由统一命令行入口承接；引导面在「会话开始/压缩前钩子」与「项目级常驻托管块」之间经最小验证择一定型，并在文档中记录选择理由。
- `REQ-27`: **IF** 纪律技能插件或上游镜像缺失 **THE SYSTEM SHALL** 降级为一句可执行的安装提示，且 MUST NOT 阻断宿主其余功能。
- `REQ-28`: **WHEN** Claude Code 端执行与 DSH 等价的动作 **THE SYSTEM SHALL** 产出与 DSH 端一致的输出结构。

**F. Codex 与 Cursor 适配器（FR-005，P1）**

- `REQ-29`: **THE SYSTEM SHALL** 为 Codex 提供三面实现：技能面经其原生技能目录、工具面经统一命令行入口、引导面经项目级幂等托管块；调用形式 MUST 与其原生命令前缀一致。
- `REQ-30`: **THE SYSTEM SHALL** 为 Cursor 提供三面实现：技能面经其原生技能目录、工具面经统一命令行入口、引导面经其常驻规则目录；调用形式 MUST 与其原生命令前缀一致。
- `REQ-31`: **IF** 体检在 Cursor 端发现自动信任类派发参数（跳过信任提示、自动批准外部工具、强制执行的组合）**THE SYSTEM SHALL** 显式输出安全警告并提示仅限受控项目；插件 MUST NOT 默认写入或开启该派发参数。
- `REQ-32`: **THE SYSTEM SHALL** 保持 Codex 与 Cursor 的适配实现各不超过 100 行。

**G. 多端只读体检与回归矩阵（FR-006，P1）**

- `REQ-33`: **WHEN** 用户请求体检 **THE SYSTEM SHALL** 输出固定五区的结构化结果：环境区、宿主区、仓库区、运行时区、触发试跑区；每区 MUST 可独立判定成功或失败，单项失败 MUST NOT 阻断其余分区。
- `REQ-34`: **WHEN** 生成环境区 **THE SYSTEM SHALL** 一次性全量探测全部必需的外部工具与平台前提，逐项给出状态、失败原因与可直接执行的修复命令，MUST NOT 一次只报一个缺失项。
- `REQ-35`: **WHEN** 生成宿主区 **THE SYSTEM SHALL** 报告当前宿主、所用集成键与扩展状态、纪律技能的安装渠道与版本、以及信任类派发参数的安全告警。
- `REQ-36`: **WHEN** 生成仓库区 **THE SYSTEM SHALL** 报告受管模板与随包版本之间的内容漂移，以及原生命令技能产物的完整性。
- `REQ-37`: **WHEN** 生成运行时区 **THE SYSTEM SHALL** 报告技能挂载情况、同名技能的跨提供者优先级冲突、外部桥接插件的存在与来源、以及待生效标记状态。
- `REQ-38`: **WHEN** 用户在触发试跑区给出一段任务描述 **THE SYSTEM SHALL** 对当前可见技能（含插件提供与用户级安装，不含仅存在于上游镜像而未安装的条目）返回按匹配度排序的候选，且 MUST NOT 执行其中任何技能；**IF** 上游镜像缺失 **THE SYSTEM SHALL** 仍基于已挂载技能给出结果，该区 MUST NOT 因镜像缺失而判失败。排序 MUST 由确定性打分决定（同一输入重复执行结果逐字一致），同分 MUST 有确定的并列次序（按技能名、再按提供者名的字典序），MUST NOT 依赖输入顺序或哈希随机化；不可被用户直接调用的技能 MUST 被显式标注排除而非静默丢弃，零分技能 MUST 仍列出。
- `REQ-39`: **THE SYSTEM SHALL** 让体检全程零写操作、可重复执行且结果一致，错误统一为「状态 + 错误码 + 说明 + 修复提示」四字段出口。
- `REQ-40`: **THE SYSTEM SHALL** 建立持续集成回归矩阵：上游维度覆盖「最新主干 / 锁定版 Spec Kit / 锁定版纪律技能镜像」，宿主维度覆盖「DSH + Claude Code」（四端阶段扩展至全部四端），每个组合执行安装 → 初始化 → 体检冒烟。
- `REQ-41`: **IF** 上游最新主干引入破坏性变更 **THE SYSTEM SHALL** 在合并前使矩阵变红，并指出漂移的具体命令/参数/契约点与需要调整的版本下界。
- `REQ-42`: **IF** 回归矩阵因网络或凭据不可用而无法执行 **THE SYSTEM SHALL** 报告为「未执行（环境不可用）」，MUST NOT 报告为通过。

**H. 渐进交付与止损（P0/P1）**

- `REQ-43`: **WHEN** 进入任一里程碑 **THE SYSTEM SHALL** 先满足其前置最小验证（引导通道在打包形态下可达、首个外部端的集成与钩子生效、其余两端的纪律技能安装方式可行），未通过 MUST NOT 进入该里程碑。
- `REQ-44`: **IF** 某里程碑的止损线被触发 **THE SYSTEM SHALL** 停在该里程碑并按预设处置（降级为固定注入、延后扩展、冻结后续端或回退目录重组），MUST NOT 以未验证状态继续叠加后续里程碑。
- `REQ-45`: **WHEN** 完成核心抽离 **THE SYSTEM SHALL** 使 DSH 端的可观察行为与既有版本 100% 回归一致（既有输入字段、输出字段、成功/失败语义与命令行为不变，新增字段与新增入口为增量）。
- `REQ-46`: **THE SYSTEM SHALL** 保持零分叉：MUST NOT 复制上游 Spec Kit 或纪律技能仓库的任何逻辑，MUST NOT 迁移或改写用户既有的普通技能，MUST NOT 复活已删除的自研安装器。

## 3. Non-Goals & Hard Constraints (业务禁区)

- **Out of Scope（不在范围内）**：
  - 跨端技能桥接本体与端间运行时状态同步（该生态位已有专门工具占据；本套件只让同一套治理层装进各端，端间无运行时耦合）。
  - 技能暴露门控（按子集暴露 / 索引条数上限）——本期降为**条件触发项**：仅在后续观察到真实上下文压力或误触发投诉时启用，本期不实现、不默认开启、不改变默认行为。
  - 复活已删除的自研安装器：更新交由包管理器与宿主插件渠道，风险敞口由依赖声明与扩展版本下界覆盖。
  - 第四端之外的新宿主（其他 CLI 与 IDE 代理）：待首批四端站稳、维护成本量化后再评估。
  - 双语描述切换、Web UI 开关面板、运行时事件硬门禁、MCP 配置转换：保持零 UI、软门禁、纯 SDD 单一职责。
  - 自动重启宿主、自动切换既有项目的集成方式、自动改写用户技能。
- **Forbidden Behavior（禁止行为）**：
  - MUST NOT 新增 npm 运行时依赖；MUST NOT 引入需要构建步骤的产物。
  - MUST NOT 在核心中出现任何宿主专属引用（包名、注册 API、全局对象），MUST NOT 让核心在缺少宿主运行时的环境里无法加载。
  - MUST NOT 因引导、体检或护栏的任何失败而阻断插件加载或使既有命令不可用。
  - MUST NOT 在体检路径上产生任何写操作（含缓存、日志文件、锁文件）。
  - MUST NOT 在引导超限时裁剪上游纪律正文。
  - MUST NOT 让规划期护栏写入文件或改变实现阶段状态。
  - MUST NOT 默认写入或开启会跳过信任提示、自动批准外部工具的派发参数。
  - MUST NOT 让同一事实（宿主能力表、重载口径、三面契约、引导文案）存在两份可编辑源。
  - MUST NOT 复制或替换宿主 profile 内已安装的插件副本（章程原则 I 的硬边界）。
- **Performance / Compatibility Bounds（性能 / 兼容性边界）**：
  - 常驻引导硬上限 1.2k token；体检单次执行（不含网络探测）不超过 5 秒；触发试跑打分在 100 条技能规模内不超过 1 秒。
  - 兼容 Node.js >= 18、ESM、跨平台（Linux / macOS / Windows）；平台受限用例（符号链接、宿主钩子、特定宿主的安装渠道）MUST 显式跳过并注明原因。
  - 每个宿主适配实现 MUST ≤100 行；核心 MUST 保持零第三方依赖。
  - 既有命令与宿主工具的输入字段、输出字段与成功/失败语义 MUST 保持向后兼容；新增字段与新增入口均为增量。
  - 单仓库单包结构 MUST NOT 拆分为多包（避免多端测试矩阵放大维护成本）。

### Success Criteria

- 用户在任一受支持终端开新会话，都不需要手工提醒「用纪律技能」或「先看 spec」；引导段在上下文压缩后依然有效，且常驻开销不超过 1.2k token。
- 「装了但不生效」类问题能在一次只读体检内定位到具体缺失项或冲突项，报告给出的修复命令可直接执行，重复执行不产生副作用。
- 未做任何配置升级的既有用户，其可观察行为与升级前完全一致；升级不需要用户改任何现有命令或参数。
- 任何一次改动之后，用户都能从一次报告里知道下一步是「重启」「新开会话」还是「什么都不用做」，且不会被历史残留标记误导。
- 新增一个终端只需实现三面契约并通过同一套契约测试，核心逻辑无需改动；四端适配实现规模均在 100 行以内。
- 上游破坏性变更在一次回归矩阵内被发现，且在合并前阻断，不进入用户项目。
- 体检与引导的所有失败路径都不会阻断插件加载，也不会让既有命令失效。

## 5. Assumptions and Dependencies

- 基线为已发布的 v0.5.x 现状（既有测试套件全绿；具体用例数以实际运行为准，断言以全绿为判据，不以固定数字为判据）。
- 上游事实来源仍是 Spec Kit 的命令行与纪律技能的本地镜像/官方渠道；本特性只读取与编排，不复制、不改写。
- 宿主差异（集成键、技能目录、调用前缀、常驻通道、重载语义）以「一张宿主能力表 + 三面契约文档」为唯一事实源；表外的新宿主按缺省能力降级，并在体检中标注「未适配」。
- 引导面在 DSH 上的存活依赖宿主提供的常驻注入通道；该通道在打包形态下是否可达 MUST 在进入对应里程碑前以最小验证确认，不可达时降级为安装期固定注入并记录该降级。
- 引导面在外部宿主上的具体形态（钩子 vs 托管块 vs 规则目录）由各端最小验证定型，规范只约束「同一份内容、抗压缩、可降级」，不预设机制。
- 技能暴露门控为条件触发项：本期不实现；其验收以「未配置时行为不变」的形式保留，未来启用时不改变默认值。
- 多集成共存假定上游的增量共存语义成立；本特性不重复实现该语义，只验证效果并在体检中呈现。
- 回归矩阵依赖公开网络与上游安装渠道；无网络环境按 `REQ-42` 报告为未执行。
- 仓库短期保留现有包名以保证连续性，品牌过渡与是否提供无前缀别名留待四端收官阶段评估，不属于本特性的验收范围。
- 平台受限的验收（宿主钩子、符号链接、特定宿主的安装渠道）在缺少相应环境的持续集成上显式跳过并注明原因，不计为失败。
